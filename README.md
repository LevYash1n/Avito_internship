# Кандидатогенерация объявлений услуг Авито

Решение находит до 50 объявлений для каждого поискового запроса. Основной пайплайн — гибридный поиск BM25, по заголовкам и эмбеддингам Granite с последующим ранжированием. Итоговый файл создаёт [`submission.ipynb`](submission.ipynb); ход экспериментов находится в [`experiments.ipynb`](experiments.ipynb).

## Запуск

Нужны Python 3.12, `uv` и три файла в корне проекта: `train.parquet`, `benchmark_items.parquet`, `benchmark_queries.parquet`. Данные доступны в [архиве задания](https://disk.yandex.ru/d/sNhfo0YOjGtufg) и не хранятся в Git. Первый запуск также загрузит локальную модель `ibm-granite/granite-embedding-97m-multilingual-r2`; обращения к внешнему API для получения предсказаний не требуются.

```bash
uv sync --frozen
uv run python run_submission.py
```

Ноутбук можно запускать и по ячейкам из корня проекта. При доступной CUDA эмбеддинги вычисляются на GPU, иначе на CPU (медленнее). Результат сохраняется в `answer.csv`; файл проверяется перед сохранением. Для экспериментов и локальной оценки используйте `experiments.ipynb`. В репозиторий также входят `eda.ipynb`, скрипты экспериментов и `experiment_log.md`.

## Описание экспериментов

Сначала был проведён EDA по трём файлам:
1) search_category=0 встречается в 0.007% строк train, но в 9.59% benchmark_queries. Для этой группы обучающих примеров почти нет; это остаётся риском для качества на benchmark.
2) Категории запроса и выбранного объявления совпадают в 99.9% train-пар. Отдельный фильтр по категории в итоговый поиск пока не добавляли.
3) Больше всего пропусков в item_rating и item_rating_reviews_count: вероятно, у многих объявлений нет отзывов. При использовании этих признаков пропуски заменялись нулями.
4) item_price=-1 в 6.5% train и 8.06% benchmark_items; это похоже на обозначение отсутствующей цены. Цену в текущую модель не добавляли.
5) У train и benchmark_items только 18 142 общих item_id. Поэтому локальную оценку проводили по запросам, чьи известные ответы есть в benchmark-корпусе.
6) В 72% положительных пар у запроса и заголовка есть общий токен; в 35% весь запрос входит в заголовок.

Для поиска использовались текст запроса и фильтры, а у объявлений - заголовок, параметры и описание: заголовок кратко называет услугу, остальные поля помогают уточнить её. Положительные пары из train использовались для обучения ранжировщика, benchmark_items - как корпус для поиска, benchmark_queries - для итогового файла.

До отправки качество проверялось по Recall@50 на val и отложенном локальном test: одинаковые сочетания текста и признаков запроса не пересекались между train/val/test, поиск выполнялся по benchmark-корпусу.

Эксперименты:
1) Бэйзлайн TF-IDF сопоставлял текст запроса с текстом объявления и дал Recall@50 = 0.21909. Это отправная точка для сравнения остальных методов.
2) BM25 улучшил результат до 0.28146. В текстах обнаружились повторяющиеся названия полей, служебные параметры и рекламные фразы: их удалили, нормализовали написание, после чего результат вырос до 0.28529.
3) По EDA часто встречалось буквальное вхождение запроса в заголовок, поэтому добавили такие объявления в выдачу: получилось 0.29715. Затем учли совпадение локации, рейтинг и число отзывов - в эксперименте результат достиг примерно 0.43.
4) Добавили ранжировщик на основании логистической регрессии: он учитывает общие слова запроса и заголовка, оценку BM25, локацию, рейтинг и отзывы. Результат - 0.52111 на val и 0.52168 на локальном test. История выбранных объявлений для знакомых запросов повысила его до 0.53837/0.53912.
5) Добавили отдельный TF-IDF по заголовкам, чтобы сильнее учитывать название услуги, и переобучили ранжировщик. Recall@50 с историей вырос до 0.57313/0.57692.
6) Попробовали предсказывать подкатегорию объявления по запросу и искать внутри неё с BM25. Правильная подкатегория часто попадала в top-3, но прямая выдача объявлений по этой схеме оказалась хуже глобального BM25, поэтому в итоговый вариант её не включили.
7) Чтобы находить подходящие объявления и без буквального совпадения слов, добавили поиск по эмбеддингам ibm-granite/granite-embedding-97m-multilingual-r2 на GPU. Объединили его с текстовым поиском и переобучили ранжировщик: Recall@50 вырос до 0.63896/0.64665 на val/test против 0.57313/0.57692 у предыдущего решения
