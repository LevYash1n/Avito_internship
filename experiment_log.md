# Журнал экспериментов: Avito Recall@50

Цель — увеличить Recall@50 при выдаче до 50 объявлений из `benchmark_items.parquet` для каждого запроса. В таблицах ниже **val/holdout** — локальная проверка с известными ответами из `train.parquet`; **test** — оценка отправленного файла на платформе. Локальные цифры нельзя напрямую приравнивать к test: запросы и покрытие разметки отличаются.

## Протокол проверки

- Удаляем дубликаты пар «полная сигнатура запроса — `item_id`». Полная сигнатура включает текст, локацию, доставку, фильтры и категорию.
- Делим сигнатуры случайно с `random_state=43` на train/val/holdout примерно 70/15/15 (`signature_split` в `experiments.ipynb`). Модель обучается только на train-сигнатурах. При этом одинаковый **текст** может встретиться в разных частях при других признаках запроса; это ближе к benchmark, чем строгое деление по текстам.
- В основном протоколе корпус фиксирован: `benchmark_items.parquet`, 189 212 уникальных объявлений. Оставляем для оценки только запросы, у которых в этом корпусе есть хотя бы один известный релевантный `item_id`; релевантность для них также ограничиваем корпусом. Это даёт корректный Recall@50 относительно доступных объявлений, но смещает проверку к тем объявлениям, которые пересекаются с train. Альтернативный протокол использует объединённый корпус benchmark и train и отвечает на другой вопрос.
- Кандидатный пул строится только из признаков запроса и объявлений. Релевантные ID участвуют в обучении ранжирования и подсчёте метрики, но не подмешиваются в val/holdout пул. `pool Recall` — верхняя граница для ранжировщика при данном пуле.
- Для выбора настроек используем val; holdout — контроль после выбора. После дополнительных итераций по holdout он перестаёт быть независимым тестом. Внешний benchmark test остаётся главным подтверждением улучшения.

## Что показывают данные

- В `train` и `benchmark_items` пересекаются только 18 142 объявления. При benchmark-корпусе большая часть train-пар не может быть положительным примером для локальной оценки.
- По EDA, у 35% положительных пар весь запрос встречается в заголовке; у 72% есть хотя бы один общий токен. Это обосновывает title-канал, но не гарантирует высокий Recall@50: точных совпадений может быть много, а релевантное объявление может лежать за top-50.
- `search_category=0` занимает около 9.59% benchmark запросов и лишь около 0.007% train-строк. Для этой группы локальная оценка почти не проверяет качество, хотя внешняя метрика её учитывает. Нужна отдельная стратегия и аудит покрытия.
- Из 2 452 benchmark запросов история train, доступная через совпадающий текст и ID в корпусе, есть лишь для 362. Этот канал не может сам по себе решить остальные запросы.
- Аудит signature split показал, что около 49.8%/50.5% val/holdout положительных пар относятся к `item_id`, уже встречавшимся среди train-позитивов. Совпадение **текста плюс фильтров** с обучением есть у 77.5%/77.0% оцениваемых val/holdout запросов, тогда как у benchmark запросов оно составляет 27.7% относительно всего train. Это ещё один признак оптимистичности локальной метрики; нужно отдельно измерять новые тексты и новые `item_id`.

## Следующие проверки

1. Обучить ранжировщик на объединённом пуле с признаками `microcat_probability` и `microcat_rank`. Сравнить с текущим reranker на тех же val/holdout.
2. Отправить уже созданный `answer.csv` с `title_rank` на платформу и записать внешний Recall@50.
3. Разложить потери по категориям и типам текста: пустые/редкие токены, точная фраза в title, видимые фильтры, знакомый/новый текст, локация. Отдельно посчитать долю запросов, где правильный ID отсутствует в пуле и где он найден, но вытеснен ранжировщиком.
4. Выполнить новый Granite-эксперимент и измерить **добавочные** релевантные ID относительно BM25/title-пула. Затем обучать ранжировщик на кандидатах от всех каналов.
5. Проверить на val условное распределение 50 слотов между каналами и запросными бакетами, зафиксировать настройку и один раз оценить holdout.

Этот файл обновляется после завершения каждого эксперимента: указываются протокол, размер пула, Recall@50, изменение относительно сравнимого baseline и вывод о том, включать ли метод в submission.
